# 13. 펌웨어 업데이트 (OTA)

돌고 있는 펌웨어가 **반대편 슬롯**에 새 이미지를 쓰고, 다 받아 검증된 뒤에야 부팅 슬롯을
바꾼다. 어느 지점에서 전원이 끊겨도 부팅 가능한 슬롯이 하나는 남는다.

```
  ap/.../ota (없음 — CLI 가 곧 인터페이스다)
        ↓
  hw/driver/ota.c        슬롯 판별 · 지우기 · 쓰기 · 전환
        ↓ uartRead / uartWrite
  HW_UART_CH_*           USB / BLE / (향후 WiFi)
```

## 13.1 부트로더는 버전을 비교하지 않는다

`bootloader/boot_flash_lp.c` 의 `BOOT_FLASH_OTA_Select()` 다.

```
OTA2 가 유효하면  → OTA2
아니면 OTA1 이 유효하면 → OTA1
둘 다 아니면 MMU 를 끄고 정지
```

"유효"는 슬롯 첫머리의 **8바이트 이미지 시그니처**(`81958711`)로 판단한다. 버전도 순번도
보지 않는다.

그래서 전환은 플래시가 **1 → 0 만 가능**하다는 성질을 그대로 쓴다. SDK 의
`change_ota_signature()` 와 같은 방법이다.

```
1. 새 슬롯에 이미지를 쓴다. 단 시그니처 8바이트는 비워 둔다
2. 다 받고 CRC 가 맞으면 시그니처를 쓴다      ← 이 순간 새 슬롯이 유효해진다
3. 옛 슬롯의 시그니처를 0 으로 덮는다          ← 지우기 없이 무효화
```

3번을 빠뜨리면 **영원히 돌아오지 못한다.** OTA2 가 유효한 한 항상 OTA2 가 이기기 때문이다.
실기 왕복으로 확인했다.

```
OTA1 실행 → 전송 → 재부팅 → OTA2 실행
OTA2 실행 → 전송 → 재부팅 → OTA1 실행
```

### 실행 중인 슬롯 판별

부트로더가 건 Flash MMU 매핑을 되읽으면 된다. 가상주소가 어느 물리주소로 가는지 보면
안다.

SDK 에도 `ota_get_cur_index()` 가 있지만 쓰지 않는다. 그 함수가 있는
`misc/rtl8721d_ota.c` 는 lwIP 와 FatFs 를 include 해서, **레지스터 두 개 읽자고 네트워크
스택 전체를 끌어오게** 된다. WiFi 없는 구성이 아예 빌드되지 않았다. `ota.c` 가 직접 읽는다.

## 13.2 지우기는 미리 하지 않는다

플래시 쓰기는 `FLASH_Write_Lock()` 안에서 돌고 그동안 **인터럽트가 꺼진다**. 1MB 를 한
번에 지우면 십수 초 동안 꺼져 있어 무선 링크가 끊긴다.

그래서 쓰기 직전에 섹터 단위로 지운다. 4KB 하나는 수십 ms 라 supervision timeout(수 초)에
한참 못 미친다.

## 13.3 프로토콜

전송이 무엇인지 모른다. `otaReceive()` 는 uart 채널 번호만 받는다.

```
보드   -> ready               준비됐다. 지금부터 원시 바이트다
호스트 -> len(2 LE) | data | sum(1)      len 0 이면 중지
보드   -> a                   받았다, 다음
          r                   체크섬이 어긋났다, 같은 청크를 다시
          e<4자리 16진>        치명적 (common/err_code.h)
보드   -> ok / e<코드>
```

**청크마다 응답을 돌려 호스트를 재운다.** 이게 없으면 보내는 쪽이 쏟아부어 수신 큐가
넘친다.

**프레이밍이 없으면 재전송 단위가 파일 전체가 된다.** 링크에서 한 바이트만 밀려도 마지막
CRC 에서야 드러나고, 그때는 747KB 를 통째로 다시 보내야 한다. 길이와 체크섬을 붙이면 그
청크 1KB 만 다시 보낸다.

### 기존 cmd 프로토콜과의 관계

`apm32e103-kit-boot` 의 cmd 프로토콜(STX + type + cmd + err_code + length + data + sum,
`cmd_uart.c` / `cmd_udp.c` 드라이버)을 검토하고 **두 가지만 가져왔다** — `err_code` 체계와
청크 프레이밍이다.

전송 추상화는 가져오지 않았다. `uart_driver_t` 가상 채널이 이미 같은 목적을 하므로
`cmd_driver_t` 를 또 두면 계층이 하나 늘 뿐이다. type 다중화도 채널을 물리적으로 나눠
두어 필요가 없다.

> 가장 큰 차이는 **프로토콜을 누가 말하느냐**다. 기존은 부트로더가 말해서 응용이 죽어도
> 업데이트가 된다. 우리는 응용이 말하므로 응용이 부팅을 못 하면 USB 로만 복구된다.
> 다만 A/B 슬롯이라 실패해도 옛 슬롯이 남아 벽돌 위험은 낮다.
>
> 나중에 NU87 전용 2nd stage 부트로더를 만든다면 그때는 cmd 프로토콜을 그대로 쓰는 것이
> 맞다. 그쪽이 애초에 그 목적으로 만들어진 것이다.

## 13.4 통로별 성격

| | 브라우저 API | 실효 속도 | 747 KB |
|---|---|---|---|
| USB | Web Serial | 10 KB/s | 약 75초 |
| BLE | Web Bluetooth | 3~10 KB/s | 1~3분 |
| WiFi | (보드에 HTTP 필요) | 수백 KB/s | 몇 초 |

USB 가 115200 에 묶인 것은 KM0 부트로더가 그렇게 설정하고 플래싱 툴과 콘솔이 같은 포트를
쓰기 때문이다. 전송 중에만 올렸다 되돌리는 것은 가능하다.

**WiFi 경로는 성격이 다르다.** 브라우저는 raw TCP 를 못 연다. PC 도구(Python)로만 쓸
거면 TCP 채널 하나 추가로 끝나지만, 웹페이지에서도 쓰려면 보드에 HTTP 엔드포인트나
WebSocket 이 필요하다.

### USB 는 선이 하나다

CLI 와 대량 전송이 같은 선을 쓴다. 그래서 **명령 에코가 응답과 같은 곳으로 돌아온다.**
첫 줄을 곧바로 응답으로 받으면 에코된 명령을 응답으로 착각한다. 기대하는 말이 나올 때까지
건너뛴다 (`tools/ota.py` 의 `wait_for`, 웹페이지의 `readLine`).

BLE 는 CLI(0xFF88/89)와 데이터(0xFF8A/8B)가 다른 특성이라 이 문제가 없다.

## 13.5 KM0 도 같이 갱신된다

슬롯에 들어가는 `km0_km4_image2.bin` 이 **KM0 image2 + KM4 image2** 다. 부트로더가 슬롯
하나에서 MMU 두 개를 걸어 KM0 는 `0x0C000000`, KM4 는 `0x0E000000` 으로 매핑한다.

오히려 이것이 필수다. KM0/KM4 는 IPC 테이블을 공유하므로 같은 SDK 커밋에서 나온 짝이어야
하고, 한 파일로 묶여 있으니 어긋날 수가 없다.

**OTA 로 못 바꾸는 것은 부트로더 둘뿐이다.**

| | 주소 | OTA |
|---|---|---|
| KM0 부트로더 | `0x08000000` 8 KB | ✗ |
| KM4 부트로더 | `0x08004000` 8 KB | ✗ |
| OTA1 / OTA2 | `0x08006000` / `0x08106000` | ✓ |

부트로더는 슬롯 밖이고 이중화가 없다. 쓰다 실패하면 복구 수단이 UART 다운로드 모드뿐이라
USB 로만 하는 것이 맞다.

## 13.6 도구

### tools/ota.py

`flash.py` 와 역할이 다르다. `flash.py` 는 다운로드 모드로 진입시켜 플래시를 통째로 굽고,
`ota.py` 는 **돌고 있는 펌웨어의 CLI 로** 반대편 슬롯에 쓴다.

```
python3 firm-sdk/tools/ota.py --port /dev/tty.usbserial-0001 \
        --image build/km0_km4_image2.bin [--reset]
```

Ctrl-C 로 중지하면 길이 0 을 보내 보드도 함께 멈춘다.

### 웹페이지

`docs/index.html` 의 펌웨어 탭이다. 파일을 고르면 **보내기 전에 어떤 이미지인지 읽는다.**

```
NU87-TINYDK · V260809R1 · WiFi + BLE · 747160 B
```

이름과 버전은 헤더 체인을 걸어가 ram 파트(load `0x10005000`)를 찾고 그 +32 의
`firm_ver_t` 에서 읽는다. 링커스크립트가 거기 고정해 둔다. KM0 이미지가 4KB 로 패딩되어
체인이 한 번 끊기므로 경계까지 건너뛰고 이어 본다.

무선 지원은 **로그 문자열**로 가른다. `wifiInit()` / `bleInit()` 가 rodata 에 그대로 남아
있다. 표식을 따로 심는 것보다 낫다 — 지금까지 만든 이미지에도 이미 들어 있어 펌웨어를
고칠 필요가 없다.

```
무선 없음   wifiInit 없음, bleInit 없음
WiFi        wifiInit 있음
WiFi+BLE    둘 다 있음
```

**BLE 로 붙은 채 BLE 없는 이미지를 고르면 경고한다.** 그대로 올리면 재부팅 순간 링크가
사라져 USB 로만 복구된다.

## 13.7 적용은 다음 부팅이다

전송이 끝난 시점에 슬롯은 이미 전환돼 있고, 지금 도는 것은 **여전히 옛 펌웨어**다. 그래서
링크도 그대로 유지된다.

자동으로 재부팅하지 않는 이유가 있다. 재부팅 전에 `ota info` 로 확인할 수도 있고, 아니다
싶으면 옛 이미지를 다시 올려 되돌릴 수도 있다. 특히 BLE 로 붙어 있을 때는 재부팅이 곧 링크
단절이라, 자동으로 해버리면 "업데이트했더니 연결이 끊겼다"가 된다.

> USB 는 보드가 재부팅해도 포트가 살아 있다. CP2102N 이 MCU 와 별개로 켜져 있기 때문이다.
> 그래서 페이지가 끊긴 줄 모르고 옛 요약을 들고 있게 되어, 재부팅 후 잠시 기다렸다 다시
> 읽는다.
